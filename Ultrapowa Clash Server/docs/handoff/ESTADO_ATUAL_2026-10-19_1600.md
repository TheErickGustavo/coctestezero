## 3. O QUE CAUSOU OS BUGS (para não repetir)

### 3.1 Crash nativo do cliente (StackOverflow em `GameApp.update`)
`UnitProductionComponent.Save()` só gravava `"t"` e `"slots"` do `unit_prod` quando havia
fila/timer. O cliente 7.65 **sempre** espera os dois campos → parser em loop → app morre
logo após o 24101. **Sempre gravar `t` e `slots`** (format do golden `24101`).

### 3.2 Produção de tropas nunca rodava
`ComponentManager.Tick()` e `GameObject.Tick()` estavam **VAZIOS** → `ProductionCompleted()`
só rodava via `SpeedUp` (gemas). Por isso o servidor ficava atras do cliente e as tropas
"reapareciam" ao usar gemas. Agora `ComponentManager.Tick()` ticka a produção (type 3) e
`ObjectManager` tem timer de 1s que tica os levels online.

### 3.3 Contador de tropas divergia
Avatar (`m_vUnitCount`, por tipo) vs storage (slots por tipo+nível). `RemoveUnitsImpl`
descontava do avatar o valor pedido (não o removido) e só achava o slot com o nível exato.
Agora: `SyncAvatarUnitCounts()` reconstrói o avatar a partir do storage (ignora o castelo
do clã `1000143` e a feitiaria) + `RemoveUnitsAnyLevel()`.

### 3.4 App não conectava
`adb reverse tcp:9341 tcp:9340` perdido + `clientVersion` 7.156 (o app manda 7.65).

### 3.5 Build
`EndOfBattleCommand.cs` não estava no `scripts/sources.rsp` → nunca era compilado.
`MySql.Data.Entity.EF6.dll` não existe → removido o provider MySQL do `App.config`
(o servidor usa SQLite: `databaseConnectionName=sqliteEntities`).

## 4. Estado do semântica do comando 603 (R-C4)

- `0x025B` = `EndOfBattleCommand`, payload = **1 int (4 bytes)**.
- O valor **NÃO é a % de destruição** (amostras: 566, 277, 693, 712, 1004, 3824, 5188, 7968
  para %s de 2% e 16%). É "damage points" (HP danificado) — **não dá para derivar a % real**.
- O servidor estima: `destruicao% = 100 × value / HP_total_atacavel_do_defensor`
  (HP total sem muros = 91.660 na vila atual). O limiar de 1 estrela (50%) funcionou em
  todos os casos testados (todos derrota, igual ao cliente).
- Log de calibração: `bin/Release/r-c4-603.log`.
